# 面向边缘异构平台的多模态大模型分布式推理系统设计与实现

## 摘要

随着大语言模型和多模态大模型在智能监控、工业巡检、移动机器人和边缘智能终端等场景中的应用不断增加，如何在算力、内存和能耗受限的边缘设备上部署大规模模型成为一个重要问题。以 Qwen3-VL 等视觉语言模型为代表的多模态模型同时包含视觉编码器和语言解码器，模型参数规模大、推理链路长、首 token 延迟高，对单一边缘设备提出了较高要求。传统的单机部署方式在 RK3588、嵌入式 GPU 或低功耗 CPU 等平台上容易受到内存容量、计算吞吐和硬件后端支持能力的限制，难以兼顾模型规模、响应延迟和系统可用性。

针对上述问题，本文设计并实现了一个面向边缘异构平台的多模态大模型分布式推理系统 DIAL。系统采用 Master-Worker 架构，将大模型推理过程中的 Transformer 层按拓扑配置划分到不同设备执行；Master 负责会话管理、token 生成循环、层级调度和 OpenAI 兼容接口，Worker 负责加载指定模型层并执行远程前向计算。系统在通信层设计了面向张量传输的轻量二进制协议，支持单层请求、连续层批量请求和紧凑批量请求，以降低分布式推理中的协议开销和网络往返次数。在模型层面，系统同时支持 Llama 类文本模型和 Qwen3-VL 多模态模型，能够处理文本、图片 base64 和 data URL 等输入形式，并实现视觉 embedding 与文本 token 序列的对齐注入。在硬件异构方面，系统接入 RKNN Runtime，支持将 Qwen3-VL 视觉编码器、文本 decode/prefill chunk 以及部分 QKV/MLP 子图部署到 RK3588 NPU 上运行，从而形成 CPU/GPU/NPU 混合推理路径。

本文围绕系统架构、通信协议、多模态推理流程、异构硬件接入和性能观测机制展开设计与实现说明，并给出面向边缘设备的实验评估方案。实验指标包括首 token 延迟、总推理耗时、生成吞吐、远端计算耗时、分布式通信开销和远程请求次数等。结果表明，该系统为边缘异构环境下多模态大模型的部署提供了一种可扩展的工程实现路径。

**关键词**：边缘计算；多模态大模型；分布式推理；Qwen3-VL；RKNN；异构计算；OpenAI API

## 1 绪论

### 1.1 研究背景

近年来，大语言模型在自然语言处理、知识问答、代码生成和多轮对话等任务中表现出较强的泛化能力。进一步地，多模态大模型将文本、图像和视频等信息统一到同一生成框架中，使模型能够完成图像理解、视觉问答、场景描述、异常检测等任务。对于智能安防、工业检测、智慧园区和移动机器人等边缘场景而言，多模态大模型具有较高应用价值。例如，在监控视频分析任务中，系统不仅需要识别画面中的对象，还需要结合自然语言问题给出语义化回答；在工业巡检任务中，系统需要理解设备图像并对异常现象进行解释。

然而，多模态大模型的部署成本明显高于传统视觉模型或小规模语言模型。一方面，视觉语言模型通常包含视觉编码器、语言模型解码器、跨模态特征对齐模块和 KV cache 等组件，推理链路较长；另一方面，模型参数量和中间激活规模较大，对内存容量和计算吞吐提出较高要求。以 Qwen3-VL-8B 类模型为例，即使采用半精度权重，单设备仍需要较大内存空间；在 CPU 或低功耗 NPU 环境下，首 token 延迟和逐 token 解码速度也可能难以满足实时应用需求。

边缘异构平台通常由 CPU、嵌入式 GPU、NPU 以及多个网络互联设备组成。不同设备在算力、内存、模型格式支持和运行时接口方面存在差异。单一设备往往无法稳定承载完整多模态大模型，而多个设备协同推理又会引入通信开销、层划分、缓存一致性和部署复杂度等问题。因此，如何在边缘异构环境中实现大模型的可配置分层部署、多模态输入处理和硬件加速，是本文关注的核心问题。

### 1.2 问题分析

在边缘平台部署多模态大模型主要面临以下挑战。

第一，单设备资源受限。边缘设备的内存和算力通常低于云端服务器，当模型参数、视觉 token 和 KV cache 共同占用内存时，单机推理容易出现内存不足或响应时间过长的问题。

第二，多模态推理首 token 延迟较高。图像输入需要经过图片解码、尺寸调整、视觉编码、视觉 embedding 注入和文本 prefill 等阶段，首 token 延迟不仅取决于语言模型，也受到视觉编码器和图像 token 数量的影响。

第三，异构硬件后端支持不一致。CPU/GPU 通常适合通用张量计算，而 RK3588 等边缘芯片提供 NPU 加速能力，但 NPU 依赖 RKNN 模型格式和固定输入形状，不一定能直接承载完整语言模型。因此，系统需要支持软件路径和硬件路径的混合执行。

第四，分布式推理通信开销不可忽视。按层切分模型后，中间 hidden state 需要在设备之间传输。如果每一层都发起一次网络请求，会产生较高往返延迟和协议开销。因此，需要对连续远端层进行合并调度，并对通信开销进行统计和分析。

第五，应用集成需要标准接口。实际应用通常希望通过 HTTP API 或 OpenAI 风格的 Chat Completions 接口调用模型，而不是直接操作底层推理代码。因此，系统需要对外提供标准化服务接口，同时保留流式输出和性能指标。

### 1.3 本文工作

针对上述问题，本文设计并实现了 DIAL 分布式多模态大模型推理系统。系统目标不是重新训练模型，而是在现有开源模型基础上，面向边缘异构环境提供可部署、可观测、可扩展的推理运行框架。本文主要工作如下。

第一，设计并实现了基于 Master-Worker 架构的分布式分层推理框架。系统通过拓扑文件描述不同 Worker 负责的模型层，Master 在推理过程中根据层归属选择本地执行或远程执行，从而支持单机、双机和多机部署形态。

第二，设计了面向张量传输的轻量二进制通信协议。协议支持握手、Worker 信息返回、单层请求、连续层批量请求和张量响应，并在请求与响应中记录远端计算耗时，为后续性能分析提供基础。

第三，实现了 Qwen3-VL 多模态推理链路。系统支持文本与图片混合输入，将图片转换为视觉 embedding，并根据聊天模板中的图片占位 token 区间完成视觉特征注入，同时支持 deepstack 中间视觉特征在语言层中的注入。

第四，接入 RKNN Runtime，实现边缘 NPU 异构加速。系统支持将 Qwen3-VL 视觉编码器部署到 NPU 上执行，也支持文本路径中的 decode/prefill chunk、QKV 子图和 MLP 子图在 RKNN 后端运行，从而形成 CPU/GPU/NPU 混合执行方案。

第五，实现了 OpenAI 兼容 API 与性能观测机制。系统提供 `/api/v1/chat/completions` 接口，支持非流式和 SSE 流式输出，并返回首 token 延迟、总耗时、生成吞吐、远端计算耗时、通信开销和远程请求次数等指标。

## 2 相关工作

### 2.1 大模型推理系统

大模型推理系统通常围绕模型加载、KV cache 管理、批处理、并行执行和服务接口展开优化。云端推理框架更关注高吞吐并发服务和 GPU 利用率，而边缘推理系统更关注单请求延迟、内存占用、硬件适配和部署复杂度。与云端环境相比，边缘环境中的设备异构性更强，网络条件更不稳定，单设备能力差异更明显。因此，直接将云端推理框架迁移到边缘设备上通常难以获得理想效果。

### 2.2 分布式模型推理

分布式模型推理通过将模型参数或计算过程划分到多个设备上执行，以突破单设备资源限制。常见方式包括张量并行、流水线并行和按层切分。张量并行需要较高带宽和紧密同步，适合高速互联 GPU 集群；流水线并行适合批量请求场景；按层切分实现相对简单，更适合边缘多设备协同部署。本文系统采用按 Transformer 层切分的方式，使每个 Worker 只需加载部分模型层，从而降低单设备内存压力。

### 2.3 多模态大模型边缘部署

多模态大模型的边缘部署不仅需要处理语言模型解码，还需要处理图像预处理、视觉编码和跨模态特征融合。相比纯文本模型，多模态模型的首 token 延迟更容易受到图像尺寸、视觉 token 数量和视觉编码器后端的影响。因此，边缘多模态推理系统需要同时优化视觉路径和文本路径。本文系统在软件实现 Qwen3-VL 视觉编码器的基础上，进一步接入 RKNN 视觉模型，使视觉编码能够在 RK3588 NPU 上执行。

### 2.4 异构硬件推理加速

边缘芯片通常集成 CPU、GPU 和 NPU。NPU 对卷积、矩阵乘和部分深度学习算子具有较高能效，但也受到模型格式、算子支持、输入形状和运行时接口的限制。对于大语言模型而言，完整模型直接转换到 NPU 可能面临动态 shape、KV cache、注意力机制和模型规模等问题。因此，本文系统采用混合执行策略：视觉编码器可整体转换为 RKNN，文本路径则支持 chunk 或子图级别的 RKNN 接入，使系统能够在稳定性和加速收益之间取得平衡。

## 3 系统总体设计

### 3.1 设计目标

DIAL 系统的设计目标包括以下几个方面。

第一，可分布式部署。系统应支持将模型不同层部署到不同设备上运行，缓解单设备内存和算力限制。

第二，多模态支持。系统应能够处理文本和图像混合输入，并支持 Qwen3-VL 类视觉语言模型的推理流程。

第三，异构硬件兼容。系统应同时支持 CPU/GPU 软件推理路径和 RKNN NPU 硬件加速路径。

第四，低侵入应用集成。系统应提供 OpenAI 兼容接口，方便外部应用以标准 HTTP 方式调用。

第五，可观测性。系统应输出推理延迟、吞吐、远程计算、通信开销等指标，便于定位瓶颈和指导优化。

### 3.2 系统架构

系统采用 Master-Worker 架构，由三类角色组成：Master、Worker 和 Client。

Master 是推理主控节点，负责模型装配、会话管理、token 生成循环、层级调度和 API 服务。对于本地层，Master 直接调用本地 Forwarder 完成前向计算；对于远程层，Master 通过 TCP 连接向对应 Worker 发送张量请求，并等待 Worker 返回计算结果。

Worker 是远程计算节点，负责加载拓扑文件中指定的模型层，并监听 TCP 请求。Worker 收到 Master 发来的张量和层信息后，将 RawTensor 还原为内部 Tensor，执行对应层的前向计算，再将结果序列化后返回 Master。

Client 是外部调用端，可以是命令行客户端，也可以是业务系统。系统提供 OpenAI 风格的 Chat Completions API，Client 只需发送标准 JSON 请求即可调用模型。命令行客户端还支持图片文件转 base64、多轮 REPL 和流式输出。

系统整体推理流程如下。

1. 启动时读取模型目录和配置文件，自动识别 Llama 或 Qwen3-VL 模型类型。
2. 读取拓扑文件，确定每一层由本地节点还是远程 Worker 执行。
3. Master 加载本地层，Worker 加载各自负责的远程层。
4. Client 发送文本或图文请求到 Master 的 HTTP API。
5. Master 对消息进行编码，必要时先执行图片预处理和视觉编码。
6. 在 token 生成循环中，Master 按层执行本地或远程前向计算。
7. 生成 token 被解码为文本，并通过 JSON 或 SSE 形式返回 Client。
8. 请求结束后返回性能指标。

### 3.3 拓扑配置机制

系统通过 YAML 拓扑文件描述 Worker 节点和层归属。每个节点包含网络地址和负责的层列表。层列表支持范围表达式，例如：

```yaml
worker1:
  host: "192.168.1.10:10128"
  layers:
    - model.language_model.layers.0-11

worker2:
  host: "192.168.1.11:10128"
  layers:
    - model.language_model.layers.12-23
```

系统启动时会将层范围展开为具体层名，并构建层到节点的映射关系。在模型装配阶段，如果某一层出现在拓扑配置中，Master 会创建远程 Client 代理；否则加载本地层。这样，分层部署策略可以通过配置文件调整，而不需要修改模型推理代码。

### 3.4 统一 Forwarder 抽象

为了统一本地层和远程层的调用方式，系统定义了 Forwarder 抽象接口。本地 Transformer 层和远程 Client 均实现该接口。对于上层模型生成逻辑而言，本地层和远程层都表现为可执行 `forward` 的模块；区别在于本地层直接执行张量计算，而远程 Client 会将请求打包后发送给 Worker。

这种设计降低了模型推理主循环与分布式通信实现之间的耦合度。对于 Llama 和 Qwen3-VL 文本分支而言，层级调度逻辑可以复用同一套 Forwarder 机制。

## 4 通信协议与远程执行机制

### 4.1 协议设计

Master 与 Worker 之间采用自定义轻量二进制协议。每条消息由固定魔数、消息长度和序列化 payload 组成。payload 使用紧凑二进制序列化方式，避免使用 JSON 或 HTTP 等文本协议传输大规模张量数据。

协议支持以下消息类型。

- `Hello`：Master 与 Worker 建立连接时的握手消息。
- `WorkerInfo`：Worker 返回运行环境、设备类型、协议能力和延迟信息。
- `SingleOp`：请求 Worker 执行单个模型层。
- `Batch`：请求 Worker 连续执行多个模型层。
- `CompactBatch`：对连续层批量请求进行紧凑编码，减少重复层名传输。
- `CompactRangeBatch`：进一步使用起始 block 和层数描述连续层范围。
- `Tensor`：Worker 返回计算结果张量和远端计算耗时。

张量通过 `RawTensor` 表示，包含原始字节、数据类型和 shape 信息。接收端根据这些信息在目标设备上还原为内部 Tensor。

### 4.2 连续远端层批处理

如果模型中多个连续层都部署在同一 Worker 上，Master 不会逐层发送请求，而是将这些层合并为一个 batch 请求。Worker 收到 batch 后，在本地连续执行这些层，最后只返回一次结果。

这种方式可以减少网络往返次数。例如，当第 0 至第 11 层都部署在同一 Worker 上时，逐层请求需要 12 次网络往返，而 batch 请求只需要 1 次网络往返。对于 decode 阶段而言，每生成一个 token 都要重复执行所有层，因此减少远程请求次数对降低分布式开销具有重要意义。

系统还支持 compact batch。当连续层的 `index_pos` 相同且 block index 连续时，Master 可以只传递首层信息、起始 block 和层数，避免在每次请求中重复传输完整层名列表。

### 4.3 性能统计

系统在远程调用过程中记录以下信息。

- 远程请求次数 `remote_requests`
- 远程总耗时 `remote_total_s`
- Worker 纯计算耗时 `remote_compute_s`
- 写入耗时 `remote_write_s`
- 读取耗时 `remote_read_s`
- 写入字节数 `remote_write_bytes`
- 读取字节数 `remote_read_bytes`

其中，分布式非计算开销定义为：

```text
distributed_overhead_s = remote_total_s - remote_compute_s
```

该指标主要反映网络传输、序列化、反序列化、协议处理和等待等开销。通过该指标可以判断当前性能瓶颈来自远端计算本身，还是来自分布式通信链路。

## 5 Qwen3-VL 多模态推理实现

### 5.1 模型配置适配

Qwen3-VL 模型包含文本配置和视觉配置。系统启动时读取模型目录下的 `config.json`，如果 `model_type` 为 `qwen3_vl`，则进入 Qwen3-VL 推理路径。系统将 Qwen3-VL 的文本子配置转换为内部 Llama 类配置，使文本分支能够复用已有的 Transformer 层结构、KV cache 和分布式 Forwarder 机制。

配置适配过程中，系统处理了 `vision_config`、`text_config`、`image_token_id`、`vision_start_token_id`、`vision_end_token_id` 和 `deepstack_visual_indexes` 等字段，为后续图文融合和 deepstack 注入提供基础。

### 5.2 聊天历史编码

系统支持 OpenAI 风格的消息格式，包括 system、user 和 assistant 角色。对于纯文本消息，系统按 Qwen ChatML 风格生成 token 序列。对于包含图片的消息，系统不会直接把图片内容写入文本，而是在 token 序列中插入图片占位区间。

图片占位区间由 `vision_start`、若干 `image_token_id` 和 `vision_end` 组成。系统同步记录每张图片对应的 `ImageSpan`，即图片 token 在文本序列中的 `[start, end)` 范围。后续视觉编码器输出的 embedding 会根据该范围写入文本 embedding 中，从而实现图像特征与文本 token 序列的对齐。

### 5.3 图片预处理与视觉编码

系统支持两种图片输入形式：`image_base64` 和 `image_url`。其中 `image_url` 支持 data URL 格式。图片输入首先被解码为 RGB 图像，然后根据运行参数进行尺寸调整。

系统提供两类 resize 策略。

第一，最大边长限制。通过 `vision_max_side` 控制图片送入视觉编码器前的最大边长，并可通过 `vision_no_upscale` 禁止小图上采样。该策略适合软件视觉编码路径，用于减少视觉 token 数和首 token 延迟。

第二，固定边长 letterbox。通过 `vision_fixed_side` 将图片缩放并补边到固定正方形尺寸，适合 RKNN 等需要静态输入 shape 的硬件后端。补边时保持原图宽高比，避免直接拉伸导致图像内容变形。

视觉编码器将图片转换为视觉 token embedding，并输出 deepstack 中间特征。主视觉 embedding 会注入到图片 token span 对应的位置，deepstack 特征则在指定语言层中进一步注入。

### 5.4 Deepstack 注入

Qwen3-VL 模型中的 deepstack 机制允许视觉分支的中间特征在语言模型不同层中参与融合。系统在视觉编码阶段收集 deepstack 输出，并在文本前向传播过程中，当执行到对应层时，将 deepstack embedding 注入到图片 token span 所在位置。

该实现使系统能够保持 Qwen3-VL 多模态结构的完整性，而不是只把最终视觉 embedding 简单拼接到文本输入中。对于图片理解任务而言，deepstack 注入有助于保留视觉信息在语言模型不同层中的融合路径。

### 5.5 Token 生成流程

Qwen3-VL 的生成流程分为首轮 prefill 和后续 decode。

在 prefill 阶段，系统根据聊天历史生成完整输入 token 序列，执行 embedding，注入视觉 embedding 和 deepstack 特征，然后通过文本 Transformer 层得到最后位置的 logits。该阶段包含图片处理和完整上下文计算，因此通常决定首 token 延迟。

在 decode 阶段，系统使用 KV cache，每次只输入新生成的一个 token。文本层根据缓存中的历史 K/V 继续生成下一个 token，从而降低单 token 解码成本。系统同时支持本地层、远程层和 RKNN 文本 chunk 参与 decode。

## 6 异构硬件加速实现

### 6.1 Vision RKNN 路径

为了降低多模态推理中的视觉编码耗时，系统支持将 Qwen3-VL 视觉编码器导出为 ONNX，并转换为 RKNN 模型。在运行时，系统通过 RKNN Runtime 加载 `.rknn` 文件，将图片张量送入 NPU 执行。

Vision RKNN 路径主要包含以下步骤。

1. 读取 RKNN 模型文件并初始化 runtime。
2. 查询模型输入输出数量、输入 shape、输出 shape 和数据类型。
3. 将图片张量转换为 RKNN 需要的布局和数据类型。
4. 调用 `set_inputs`、`run` 和 `get_outputs` 完成 NPU 推理。
5. 将输出缓冲区转换回系统内部 Tensor。
6. 第一组输出作为主视觉 embedding，其余输出作为 deepstack 特征。

由于 RKNN 通常要求静态输入 shape，系统在使用 Vision RKNN 时会检查 `vision_fixed_side` 是否与 RKNN 模型输入边长一致，避免输入尺寸不匹配导致推理失败。

### 6.2 Text RKNN Chunk 路径

完整语言模型直接部署到 RKNN 上存在较大难度，主要原因包括自回归 decode 过程中的 KV cache、动态上下文长度、注意力 mask 和多层输出状态管理等。为此，系统采用文本 chunk 方式，将若干连续语言层导出为独立 RKNN 子模型。

Text RKNN 路径支持 decode chunk 和 prefill chunk。decode chunk 用于单 token 解码阶段，输入包括当前 hidden state、RoPE 信息、历史 KV cache 和 past mask，输出包括新的 hidden state 和各层 present KV。系统内部维护 RKNN 侧 KV 数据，并在必要时与软件路径的 cache 进行同步。

对于不同上下文长度，系统支持 bucket 机制。即 RKNN 模型可以预先支持若干 past length bucket，例如 128、256、512、1024。运行时根据当前上下文长度选择合适 bucket，并对 KV cache 进行 padding 或截断，以适配 RKNN 输入形状。

### 6.3 QKV/MLP 子图 RKNN 路径

除了完整文本 chunk，系统还支持更细粒度的子图加速方式。QKV RKNN 路径只将文本层中的 `q_proj`、`k_proj` 和 `v_proj` 投影放到 RKNN 上执行，RoPE、KV cache、attention softmax 和后续计算仍由软件路径完成。该方式对 KV cache 和动态 shape 的侵入较小，稳定性更高。

MLP RKNN 路径则将文本层中的前馈网络子图下沉到 RKNN，支持完整 MLP 或 gate/up、down 分段执行。该路径主要用于 decode 阶段的 `[1,1,hidden]` 输入形状，适合在边缘 NPU 上加速部分矩阵计算。

通过这些不同粒度的 RKNN 接入方式，系统可以根据模型转换成功率、NPU 内存、运行稳定性和性能收益选择合适部署策略。

## 7 OpenAI 兼容 API 与客户端

系统提供 `/api/v1/chat/completions` 接口，输入格式接近 OpenAI Chat Completions。请求体包含 `messages` 和 `stream` 字段。非流式模式下，系统等待整段回复生成完成后返回 JSON；流式模式下，系统通过 SSE 持续发送增量 token，并在最后一个 chunk 中附带性能指标。

返回指标包括：

- `ttft_s`：首 token 延迟。
- `total_s`：请求总耗时。
- `tokens_per_second`：平均生成速率。
- `decode_tokens_per_second`：decode 阶段生成速率。
- `distributed_overhead_s`：分布式非计算开销。
- `remote_compute_s`：远端 Worker 纯计算耗时。
- `remote_requests`：远端请求次数。

命令行客户端支持以下能力。

- 单次文本提问。
- 图片文件自动 base64 编码并作为多模态请求发送。
- REPL 多轮对话。
- 流式输出。
- 打印服务端返回的性能指标。

这些能力使系统既可以作为底层推理框架使用，也可以作为面向应用的模型服务使用。

### 8.9 实验分析写法

实验结果完成后，本节可以从以下角度分析。

第一，Vision RKNN 对首 token 延迟的影响。若视觉编码耗时显著下降，说明多模态模型的视觉路径适合通过 NPU 加速。

第二，分布式层切分的收益与代价。若远端计算耗时下降但分布式开销上升，需要分析当前层划分是否合理，以及网络传输是否成为瓶颈。

第三，连续层批处理的效果。若 Batch 和 CompactBatch 减少了 `remote_requests` 和 `distributed_overhead_s`，说明通信协议优化有效。

第四，不同图片尺寸的性能差异。图片尺寸越大，视觉 token 数通常越多，TTFT 越高。需要结合输出质量选择合适输入尺寸。

第五，网络带宽敏感性。低带宽环境下，分布式推理收益可能被通信开销抵消；高带宽环境下，远程计算加速更容易体现。

## 9 系统特点与不足

### 9.1 系统特点

第一，系统具备统一的本地与远程层执行抽象。通过 Forwarder 接口，模型主循环不需要关心某一层是在本地计算还是远程 Worker 计算。

第二，系统支持 Qwen3-VL 多模态推理，包括图片占位 token、视觉 embedding 注入和 deepstack 特征注入，能够覆盖图文输入场景。

第三，系统支持多种异构加速路径，包括 Vision RKNN、Text RKNN Chunk、QKV RKNN 和 MLP RKNN，便于在不同硬件能力下选择部署方式。

第四，系统提供 OpenAI 兼容 API 和命令行客户端，降低上层应用集成成本。

第五，系统内置较完整的性能指标统计，能够区分模型计算开销和分布式通信开销。

### 9.2 当前不足

第一，当前层划分主要依赖静态拓扑文件配置，尚未实现根据运行时状态自动调整层划分的机制。

第二，RKNN 文本路径对模型转换、输入 shape、bucket 和运行时能力有较强依赖，不同模型版本和 toolkit 版本可能需要额外适配。

第三，分布式推理目前以单请求生成流程为主，对高并发批处理服务的支持仍有限。

第四，实验结果仍需进一步补充，包括不同设备、不同网络条件和不同模型规模下的系统性评估。

第五，系统中部分 RKLLM 路径仍处于验证阶段，当前论文主体不将其作为核心完成能力。

## 10 总结与展望

本文设计并实现了一个面向边缘异构平台的多模态大模型分布式推理系统 DIAL。系统围绕边缘设备资源受限、多模态推理首 token 延迟高、异构硬件后端差异大和分布式通信开销明显等问题，构建了 Master-Worker 分层推理架构，设计了轻量张量通信协议，实现了 Qwen3-VL 多模态推理链路，并接入 RKNN Runtime 以支持视觉编码器和部分文本子图的 NPU 加速。

系统通过静态拓扑配置实现模型层级划分，使多台边缘设备能够协同承担大模型推理任务；通过连续层批处理和紧凑批量协议减少远程请求次数；通过 OpenAI 兼容 API 和性能指标输出支持实际应用集成和性能分析。整体来看，本文工作为多模态大模型在边缘异构平台上的部署提供了一种可行的系统实现方案。

未来工作可以从以下方向继续扩展。第一，引入基于运行时 profiling 的自动层划分策略，减少人工拓扑配置成本。第二，进一步完善 RKNN/RKLLM 文本模型部署链路，提高 NPU 对语言模型 decode 阶段的覆盖率。第三，支持多请求并发调度和批处理，提高服务吞吐。第四，引入更完整的质量评估数据集，在性能指标之外评估多模态回答准确性。第五，针对视频流场景加入帧缓存、图像 embedding 复用和事件触发机制，降低连续图像理解任务的整体开销。
